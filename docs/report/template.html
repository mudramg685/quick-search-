1Abstract

QuirkSearch is a complete, self-contained web search engine. It does not call any third-party search API: every stage — fetching pages over HTTP, extracting and normalizing text, building an inverted index, storing it in a relational database, ranking with BM25 and presenting results — is implemented in this project.

The crawler performs a polite, concurrent breadth-first traversal of the link graph (robots.txt, per-host rate limiting, timeouts, URL canonicalization and SHA-256 duplicate detection). Pages are tokenized, stop-word filtered and stemmed with a from-scratch implementation of the Porter algorithm, then written — one ACID transaction per page — into a normalized SQLite schema whose document-frequency counters are maintained by triggers. At query time an in-memory hash-map index answers queries by term-at-a-time BM25 accumulation and a bounded min-heap selects the Top-K. The running system indexes {{documents}} pages from {{domains}} domains ({{terms}} terms, {{postings}} postings); retrieval and ranking take {{ret_mean}} ms on average and a complete search request including snippets is served in {{http_p50}} ms (median, HTTP end-to-end). The backend is covered by {{tests}} automated tests with {{coverage}} statement coverage.

2Problem statement

Searching a collection of documents by scanning every document for every query costs time proportional to the size of the collection, which quickly becomes unusable. Real search engines solve this with a pipeline of networking, storage and algorithmic techniques — but these are usually hidden behind APIs. The goal of this project is to build that pipeline end-to-end, in a way that is small enough to understand completely yet faithful to how production engines work, and to make each Computer Networks, DBMS and DSA concept visible in working code rather than only in documentation.

3Project objectives

  1. Crawl web pages from seed URLs with a custom, polite, fault-tolerant crawler.
  2. Extract titles, descriptions, headings, body text and links; clean and normalize the text.
  3. Build an inverted index storing term frequencies and document frequencies.
  4. Persist documents, the index and operational data in a properly designed relational database.
  5. Accept queries, retrieve candidate documents efficiently and rank them with BM25.
  6. Return the Top-K results with highlighted, query-dependent snippets.
  7. Expose everything through a validated REST API and a polished, responsive web interface.
  8. Provide analytics on crawling, indexing and searching, backed by real measurements.

6Overall system architecture

The system has three tiers. The browser talks JSON over HTTP to a FastAPI server. The server owns a search engine core written in plain Python and a SQLite database. Crawls run on a background thread with their own asyncio event loop, so searches continue to be served while pages are fetched and indexed (SQLite's write-ahead log lets readers proceed during writes). The in-memory index is a cache of the durable postings in SQLite: it is rebuilt at startup and refreshed every 15 indexed pages and at the end of each crawl, then swapped in atomically.

8Web crawler architecture and working

The web is a directed graph whose vertices are pages and whose edges are hyperlinks. The crawler explores it breadth-first from the seed URLs: a FIFO asyncio.Queue is the frontier, so all pages at distance d from a seed are visited before those at distance d+1, and max_depth bounds the traversal. N worker coroutines (default 4) consume the queue concurrently; because almost all time is spent waiting on the network, concurrency overlaps those waits.

Key mechanisms

  • URL canonicalization (RFC 3986 §6). Relative links are resolved against the page (or <base href>); scheme and host are lowercased; internationalized host names are IDNA-encoded (the form DNS uses); default ports are dropped; dot-segments are removed; percent-encoding is normalized; query parameters are sorted and tracking parameters (utm_*, fbclid…) removed; fragments are dropped because they never reach the server. Example: HTTP://Example.COM:80/a/./b/../c#top → http://example.com/a/c.
  • Visited set. The SHA-1 hash of each canonical URL is inserted into a Python set when the URL is enqueued, so every vertex enters the frontier at most once — O(1) average membership tests and O(V+E) total work.
  • Politeness. robots.txt is fetched once per origin and cached; 4xx means “allow all”, 5xx/unreachable means “disallow all” (RFC 9309). A per-host lock and timestamp enforce at least 0.5 s between requests to one host (or the site's Crawl-delay, capped at 5 s). Crawls are restricted to the seeds' domains by default.
  • Robustness. Every failure mode is classified and stored in crawl_errors; a single bad page can never stop a worker. A page budget is reserved atomically (no await between check and increment) so concurrent workers never exceed max_pages.
  • Duplicate content. The SHA-256 fingerprint of the normalized text is compared with fingerprints already in the database, detecting mirrors served under different URLs.
The bundled QuirkPedia corpus (39 linked articles) is served by the backend itself at /corpus and crawled over real HTTP, so the engine works offline. It deliberately contains a robots-blocked page, an exact duplicate, a noindex draft and a broken link; the first crawl correctly produced exactly one error of each kind (§22).

The Porter stemmer

Implemented from M. F. Porter, “An algorithm for suffix stripping” (1980). A word is viewed as [C](VC)m[V], where m (the measure) counts vowel–consonant sequences. Five ordered steps apply suffix rules guarded by conditions on m, e.g. (m>0) ATIONAL → ATE turns relational into relate, and step 1 handles plurals and -ed/-ing (caresses → caress, ponies → poni, motoring → motor, hopping → hop). The implementation passes 82 of Porter's published examples and agrees with NLTK's reference implementation on every word of the corpus except three words of 1–2 letters, which Porter's own C code intentionally leaves unchanged.

10The inverted index

A forward index lists the terms of each document. An inverted index flips it: for every term it stores a postings list — the documents containing that term together with the term frequency (tf). The document frequency df(t) is the length of that postings list.

Why it is faster than scanning

A scan must tokenize and examine all N documents for every query: O(total text). With the index, a query for network performs one O(1) hash lookup and reads df(network) postings. The cost of a query is O(Σ df(ti)) — only documents that contain a query term are ever touched. Measured on this system, a lookup takes {{idx_ms}} ms versus {{scan_ms}} ms for re-scanning the documents, a factor of about {{speedup}}× (§23).

How document frequencies are calculated

In memory, df(t) is literally len(postings[t]), so it can never drift from the postings. In the database it is cached in terms.doc_freq for O(1) IDF lookups, and two triggers keep it exact: AFTER INSERT ON postings increments it, AFTER DELETE ON postings decrements it — whichever code path (explicit delete or ON DELETE CASCADE) modifies postings. A test asserts after every operation that doc_freq equals COUNT(*) of postings for every term.

How the index is updated

  • New page: insert the document row, insert one posting per distinct term (triggers increment df), upsert vocabulary words, replace outgoing links — all in one transaction.
  • Re-crawled page: in the same transaction, delete its old postings (triggers decrement df), garbage-collect terms whose df reached 0, update the row, insert new postings. The document id is stable, so the update is incremental — no global rebuild.
  • In memory: the crawl service rebuilds the hash-map index from SQLite every 15 pages and at job end ({{load_ms}} ms for the current index) and swaps the reference atomically; queries in flight keep using the previous snapshot.

Normalization

The schema is in third normal form: atomic columns (1NF); no partial dependencies on composite keys — e.g. postings holds only term_freq, which depends on the whole (term, document) key (2NF); and no transitive dependencies — the domain name is not repeated in every document row but stored once in domains, and seed URLs live in crawl_job_seeds instead of a delimited string (3NF). The only deliberate denormalization is terms.doc_freq, a derivable aggregate cached for performance and kept consistent by triggers.

Transactions and durability

Connections run in autocommit mode and transactions are explicit: BEGIN IMMEDIATE … COMMIT, with ROLLBACK on any exception. Each page is indexed atomically, so a crash can never leave a half-indexed document — a test raises an exception mid-transaction and verifies nothing was written. WAL journaling lets readers proceed during writes; synchronous=NORMAL is durable at checkpoints. At startup, jobs still marked running are recovered as failed. Persistence was verified on the real server: {{persist_docs}} documents and {{persist_terms}} terms before a restart and the same counts after it.

13BM25 ranking

QuirkSearch ranks with Okapi BM25, the default similarity of Lucene and Elasticsearch. For a query Q with terms q1…qn and a document D:

score(D,Q) = Σi IDF(qi) · tf(qi,D) · (k1 + 1)tf(qi,D) + k1 · (1 − b + b · |D| / avgdl)
IDF(q) = ln ( 1 + N − df(q) + 0.5df(q) + 0.5 )
SymbolMeaningValue here
Nnumber of indexed documents{{documents}}
df(q)documents containing q (postings-list length)per term
tf(q,D)field-weighted frequency of q in D (title ×3)per posting
|D|, avgdldocument length and average length in tokensavgdl = {{avgdl}}
k1term-frequency saturation1.2
blength-normalization strength0.75

Mathematical intuition

  • IDF rewards rare terms. A term in few documents discriminates well; “bm25” carries far more information than “data”. The “1 +” inside the logarithm (Lucene's variant) keeps IDF positive even for terms in more than half the documents.
  • Saturating tf. As tf → ∞ the fraction approaches k1+1 = 2.2: the first occurrence matters most and keyword stuffing has bounded benefit — unlike TF-IDF, where score grows linearly with tf.
  • Length normalization. The denominator grows with |D|/avgdl, so a long page that mentions a term once in passing does not beat a short, focused page. b=0 disables this; b=1 normalizes fully.

These properties are verified by unit tests (monotonic IDF, bounded and diminishing tf contribution, shorter-document preference). Each result in the UI exposes its per-term contributions (“Why this result?”), and a test checks that they sum to the total score.

15Top-K retrieval and DSA explanation

After scoring, m candidate documents have scores, but the user sees only k = 10 per page. Sorting all candidates costs O(m log m). Instead heapq.nlargest(k, …) keeps a min-heap of size k: each candidate is compared with the heap's minimum (the weakest of the current best k) and replaces it only if better, costing O(log k). Total: O(m log k) time and O(k) extra memory. For page p, the engine asks for the top p·k and slices the last k, so deep pages remain correct. A test verifies that the heap returns exactly the same ranking as a full sort.

Snippet selection — two-pointer sweep

Snippets show the 32-word window containing the most distinct query terms. Words are first filtered with an O(1) prefix test (Porter only rewrites suffixes, so a word can stem to a query term only if their first two letters agree), then a two-pointer sweep over the m matching positions maintains term counts incrementally — O(n) cheap filtering plus O(m) window work. This, together with per-thread connection reuse and bounded snippet scanning, reduced end-to-end latency from 100–200 ms to the figures in §23.

Autocomplete — tries

A trie over {{vocab}} surface words (weighted by corpus frequency) and a second trie over popular past queries power suggestions: walking to the node of the typed prefix costs O(P), and the k heaviest completions below it are selected with a heap. “Did you mean” compares an unknown word against vocabulary words sharing its first letter using Levenshtein dynamic programming with early termination once every cell of a row exceeds the edit limit.

25Limitations

  • No positional index — exact-phrase and proximity queries are not supported; multi-word queries are ranked bag-of-words (with optional +term AND semantics).
  • No JavaScript rendering — pages whose content is produced client-side are indexed as their static HTML only.
  • Porter stemming limits — e.g. “trie” → trie but “tries” → tri, so they do not conflate; over-stemming can merge unrelated words. English-only stop words and stemming.
  • Some sites refuse generic bots — Wikipedia answers 403 under Wikimedia's robot policy; the crawler respects this rather than impersonating a browser.
  • Single node — one SQLite writer and an in-memory index sized by RAM; fine for tens of thousands of pages, not for the open web. The full index is reloaded after crawls (≈{{load_ms}} ms now; grows with P).
  • Boilerplate — footer/related-link text on some sites is indexed (“related”, “documentation” are among the highest-df terms); BM25's IDF largely neutralizes them.
  • Duplicate detection is exact (SHA-256); near-duplicates are not detected.

26Future enhancements

  • Positional postings for phrase and proximity scoring; BM25F with per-field lengths.
  • PageRank over the stored links graph, blended with BM25.
  • SimHash/MinHash near-duplicate detection; sitemap.xml discovery; conditional GET (ETag/If-Modified-Since) for cheap re-crawls; scheduled re-crawling.
  • PostgreSQL backend (repository already isolated), incremental in-memory updates instead of full reloads, compressed (delta + varint) postings.
  • Query-log-based learning to rank, synonyms, multilingual analyzers.
  • Docker Compose packaging and CI running the test suite on every commit.

27Conclusion

QuirkSearch demonstrates that the core of a web search engine can be built, understood and measured end-to-end. Computer Networks concepts appear as a polite, concurrent, failure-tolerant HTTP crawler; DBMS concepts as a normalized, constraint-checked, transactional schema with triggers and purposeful indexes; and DSA concepts as the hash-map inverted index, BFS traversal, heap Top-K, tries, dynamic programming and a hand-written Porter stemmer. The result is a working product — {{documents}} pages indexed, sub-millisecond ranking, {{tests}} passing tests — whose every ranking decision can be explained to the user, one term at a time.
